# Language

常に日本語で回答してください。説明・コメント・ユーザーとのやり取りはすべて日本語で行うこと。技術用語やコード識別子は元の形のまま使用する。

日本語の正書法を完全に守り、すべての送り仮名・濁点・半濁点・特殊文字を正確に使用すること。

# URLの書き方

会話の返答、ドキュメント、PRの本文など、Markdownとして表示される文章では、URLを裸で書かない。自動リンクはURLの終わりを空白か`<`で判断するので、URLの直後の全角の文字（「）」「に」など）までリンクに含めてしまう。日本語と英数字の間には空白を入れないので、空白で区切ることもできない。

- 文中では、Markdownのリンクで書く。例：`[PR #23](https://github.com/ngram/skills/pull/23)`
- URLそのものを見せたいときは、山括弧で囲む。例：`<https://github.com/ngram/skills/pull/23>`
- コードブロックとインラインコードの中のURLは、リンクにならないので、そのままでよい
- コミットメッセージはMarkdownとして表示されないので、対象外とする

# 日本語の文章

日本語で書く文章は、ドキュメント（README、マニュアル、docs/、PRの本文、コードのコメント）もユーザーへの返答も、次の規則に従う。ドキュメントの読み手は、このセッションの会話も作業の途中経過も知らない。返答の読み手であるユーザーも、Claudeが作業の中で付けた呼び名や、読んだファイルの中身は知らない。どちらも、読み手がその文章だけで理解できるように書く。規則に無い場面でも、この目的に照らして判断する。

## 語の選び方

- 具体的な技術用語を使う。「口を足す」「条件窓に足す」「CSVを持ち帰る」のような、意味の通らない抽象化や言い換えをしない。読み手が、何を指しているかを推測しなければならなくなるため。
- 動詞の連用形を名詞にした和語（「試し」「写し」「確かめ」）を使わない。「試行」「コピー」「確認」のように、技術文書で慣用されている語を使う。動詞の「試す」「写す」「確かめる」は、そのまま使ってよい。
- カタカナ語のまま定着している用語を、和語や漢語に直さない。「版」「窓」「口」「枝」「署名」ではなく、「バージョン」「ウィンドウ」「エンドポイント」「ブランチ」「シグネチャ」と書く。迷ったら、読み手が画面、コマンド、公式のドキュメントで目にする語を選ぶ（「デジタル署名」のように漢語が定着している語は、そのまま使う）。
- 機能は、画面やドキュメントにある正式な名前で書く。「暗い版（ダークモード）」のように、言い換えた語を先に置かない。
- コードのシンボルを一般名詞のように使わない。「`fetchUser`が失敗したら」ではなく、「ユーザー情報の取得が失敗したら」と書く。シンボルそのものを指すときは、インラインコードにして何であるかを添える（「`fetchUser`関数」）。
- 離れた場所で定義した記号や番号（SPEC-01など）は、初めて出す箇所で名前を併記する（「SPEC-01（ログインの仕様）」）。記号だけだと、読み手が定義を探しに行かなければならないため。
- 作業中にしか通じない言い回し（「例の件」「案B」「さっきの修正」「新方式」）を書かない。指している中身をそのまま書く。

## 文の組み立て

- 無生物主語の他動詞文を多用しない。「検索が返る」「この設定が高速化を可能にする」ではなく、「検索結果が表示される」「この設定にすると速くなる」と書く。
- サ変動詞の連用形（「〜し、」）で文をつなぎ続けない。「設定し、確認し、実行する」のように並べず、文を分ける。手順なら番号付きの箇条書きにする。
- 唐突に否定から書き始めない。まず何であるか、何をするかを書き、否定や除外はそのあとに足す。
- 口語（「〜しちゃう」「ちゃんと」「〜って」）を混ぜない。文体は、常体か敬体のどちらかにそろえる。
- 短くまとめる前に、まず正しい日本語の文で書く。助詞を落として名詞を並べた句や、主語と述語の対応が崩れた文で済ませない。

## 書く内容

この節は、ドキュメントだけに当てはめる。返答では、行ったことと結果を報告してよい。

- 人の意思決定を主語にして書く。ドキュメントは作業ログではないので、「〜を確認した」「〜を修正した」という経緯ではなく、「〜にする」「〜のため」という決定とその理由を書く。
- 書くのは、そのプロジェクトで選んだ判断と、コードから読み取れない意図・経緯・前提に限る。コードを読めば分かることと、ほかに妥当な選択肢の無い一般論は書かない。
- 同じことを複数の箇所に書かない。参照が必要なら、正とする箇所を1つに決めてリンクする。

## 書いたあとの点検

- 書き終えたら、上の規則に反する箇所が無いかを読み直して直す。ドキュメントは、文脈を知らない読み手として読み直す。
- 規則で拾えない分かりにくさに気付いたら、ユーザーに伝え、規則に足すかを相談する。足すときは、既にある規則と重ならないかを確認し、重なるならまとめる。

# 日本語ドキュメントの文章規範

README.md、CONTRIBUTING.md、CHANGELOG.md、docs/配下、plan/配下のPlanファイルなど、リポジトリの日本語ドキュメントを新規に書く、更新する、推敲するときは、作業前に日本語技術文書の文章規範を読み、それに従う。

- Claude Codeでは`japanese-tech-writing`スキルを読み込む。
- スキルの仕組みがない環境では、`~/.claude/skills/japanese-tech-writing/SKILL.md`を直接読む。
- 規範ファイルが見つからない場合は、その旨を報告してから作業する。
- 同じセッション内で同じドキュメントに何度も追記する場合も、追記のたびに書いた箇所を規範で点検する。最初に読んだだけで済ませない。

規範は書籍原稿を想定しているため、リポジトリのドキュメントでは次のように読み替える。

- 「本書」「本章」など書籍を前提とした語は使わない。
- インストール手順、コマンド、設定例は、箇条書きとコードブロックで示すことを優先する。
- 論証の構成に関する規則は、設計方針や背景を説明する節に適用する。手順だけの節には適用しなくてよい。

次のものは対象外とする。

- ソースコード中のコメント、コミットメッセージ、PRの説明文
- 英語で書かれたドキュメント

# Tool Usage (Windows 環境)

## シェルコマンドのツール選択

- `go build`/`go test`/`go run`などのGoコマンド → **PowerShell ツール**を使う
- `git`コマンド → **PowerShell ツール**を使う
- その他のCLIツール（npm, dockerなど）→ **PowerShell ツール**を使う
- POSIXスクリプトが必要な場合のみ **Bash ツール**を使う

## 専用ツールを優先する

- ファイル内容の検索（grep相当）→ **Grep ツール**を使う（Bashで`grep`を実行しない）
- ファイルのパス検索（find相当）→ **Glob ツール**を使う（Bashで`find`を実行しない）
- ファイルの読み込み（cat相当）→ **Read ツール**を使う（Bashで`cat`/`head`/`tail`を実行しない）

# Plan ドキュメント作成ルール

ユーザーから「実装計画を作成して」「Planを書いて」「設計してから実装して」など、実装前に計画を立てることを求められたら、`plan-create`スキル（claude.aiから同期したものは`anthropic-skills:plan-create`）を読み込み、その手順でPlanを書く。

- Skillが自動で読み込まれないときは、`~/.claude/skills/synced/*/plan-create/SKILL.md`か`~/.claude/skills/plan-create/SKILL.md`を直接読む。
- どちらも無ければ、`plan-create`が入っていないことと入れ方（claude.aiに`plan-create.skill`を入れる）を伝え、実装には進まない。
- **Planを書いたら、ユーザーに「実装して」と言われるまで実装に進まない。**

# PRのマージ

PRをマージしたら、マージしたブランチを次の順で削除する。

1. そのブランチのworktreeの削除（`git worktree remove <パス>`）
2. ローカルのブランチの削除（`git branch -d <ブランチ>`）
3. リモートのブランチの削除（`git push origin --delete <ブランチ>`）

- 削除するのは、マージしたPRのブランチだけにする。ほかのセッションが作ったworktreeとブランチは削除しない。
- worktreeに未コミットの変更があって`git worktree remove`が失敗したときは、`--force`で消さずにユーザーに伝える。
- リモートのブランチが既に無いときは、手順3を飛ばす。
